# Director Pattern: for an agent

**[v1.0.0](https://github.com/bladnman/director_pattern/releases/tag/v1.0.0) · October 23, 2026.**
The release names a published source revision; installation and update checks still
pin exact commits and compare the package tree under the canonical update protocol.

This site explains the method. The authoritative installation package is published
at https://github.com/bladnman/director_pattern/tree/main/pattern . Read its
[README](https://github.com/bladnman/director_pattern/blob/main/pattern/README.md)
and follow its
[INSTALL](https://github.com/bladnman/director_pattern/blob/main/pattern/INSTALL.md)
when the user requests adoption. Merely reading this guide is not an adoption request.

An installing agent need not already be a Director. Establish the method's
separation of responsibilities: every fresh actor receives a small shared
bootstrap, follows one project-owned role index, and reads its selected standalone
definition and references before action. Explicit assigned role and responsibility
route first; only an unassigned project conversation defaults Director. Missing,
conflicting, or incomplete delegated assignments clarify with the assigner; they
never fall back to Director.

First installation audits the entire loaded startup instruction chain for
size and misplaced responsibilities. Preserve shared project authority and exact
specialist rules, moving those rules into maintained definitions/contracts and
registering them in the same reachable index. Do not invent an abstract of the
pattern in AGENTS.md or merely append a hook to an enormous startup file. New
recurring responsibilities follow that same standalone-file and index discipline.
The package's [startup procedure](https://github.com/bladnman/director_pattern/blob/main/pattern/engine/references/STARTUP.md)
provides integration and fresh-host verification steps. Updates select the audit
and trial scope from affected changes under the update protocol below; routine
changes reuse still-applicable startup evidence.

## Install request

The visitor copies this into the agent already working in the target project:

```text
Install the Director Pattern in this project: https://director.metal-sole.com
```

When the user actually authorizes that request, continue directly with the
canonical GitHub installation protocol linked above. Do not send the user back
to this website to repeat the same request. Resolve published
GitHub main to one exact reviewed commit and read the package at that revision.
Copy only the manifest-selected payload into the target project's `.director/`.
Preserve existing instructions, local adaptations, project context,
unfinished work, and the canonical tracker. Do not copy this website, maintainer
material, repository metadata, or private source material into the installation.
The installed `.director/` is committed with the target project so work continues
on another machine or in a cloud checkout; the canonical INSTALL guide names the
few machine-local files it keeps out of Git and warns once about a public remote.

The method gives the project a Director who discusses, decides, keeps unfinished
commitments, and accepts each outcome. The Director entrusts each complete outcome
to one Request Manager, who owns its planning, specialist tasks, evaluation,
rework, and follow-up; a specialty is a task within the outcome, not a reason for
another manager. Specialists execute, and one shared recorder handles routine
state. The Director may dispatch substantial independent analysis that returns a
proposal; no intake layer is mandatory. Assignment roles are only `worker` and
`director`; Request Manager and Recorder are maintained responsibilities, not new
role values. A new project conversation defaults to its Director; explicit
assignments determine bounded roles and authority. Inherited history does not
grant a role. Follow current package contracts for the full rules.

PROJECT records enduring context and canonical locators: the role index (reuse
maintained roles and guardrails), capability/authority policy, Recorder routing
policy and state location, and the identity roster location. Resolve current host
controls when used. Model/version IDs, current agents or teams, capacity, tools,
permissions, and setup observations belong in assignment/receipt/activity evidence,
not PROJECT or another loaded environment cache. A missing applicable definition
stays a visible gap; do not invent generic
specialists to fill it.

Tracked is the default; lean is an explicit option. Existing trackers remain
canonical. An installation does not add a service, scheduler, runtime, or
automatic wakeup, and promises no live agents. Host capability limits must stay
visible.

## Verify an installation

```text
Verify the Director Pattern installation in this project. Check the loaded startup wiring, required files, configured mode, role index, Recorder route, and pinned source revision. Report any gaps and distinguish setup from current worker activity.
```

The website cannot inspect the visitor's project. Distinguish static wiring and
disposable fixtures from real fresh-host trials. Verify unassigned Director
startup, assigned reader/writer/reviewer/test definition loading before action,
missing/conflicting role clarification, discovery of a newly indexed role, and
upgraded startup files without relocated duties or competing defaults. Record
observed reads/acknowledgments and action sequence; label unrun trials pending.

For the separate Director identity check, resolve the assignment role
first. Only the project Director requests the current-conversation setup check:
a Small recorder checks actual wiring, required files, project mode/state, and
whether PROJECT names the role index, enduring capability/authority policy,
Recorder routing policy, and identity roster location; the Director judges that
receipt and its own resolved role.
The check runs in the background when the Director first staffs work and never
delays an answer. Its results stay in the conversation or receipt, not PROJECT;
installation provenance and acceptance live in PROJECT's authoritative receipt.
Request Managers receive the checked facts in their assignment, and workers,
reviewers, and recorders omit the badge without launching this Director-only check.
Only a checked project Director uses `🎬 Director Pattern · tracked` or
`🎬 Director Pattern · lean` initially, then `🎬` on later Director replies.
Managers and other actors use an assigned identity such as `🐙 Contract —`, never
the badge. The badge identifies checked setup and role, not behavioral
verification or live managers or workers. Missing setup/capabilities remain
visible without the marker.

The four sparse markers have distinct meanings: `🎬` identifies the checked
project Director, `❓` marks actionable questions/decisions, `🖐️` marks user-only
actions, and `📋` introduces the periodic situation-report block with the exact
heading **📋 SitRep**. Reserve that heading for report blocks so the user can scan or skip
them; do not attach it to every progress sentence. A checked Director keeps its
required `🎬` response prefix before the report block.

Use a periodic overview after several minutes of otherwise quiet managed work or
when several developments or workstreams benefit from one combined report.
Ordinary replies, worker returns, and status changes do not automatically need a
full SitRep. Communicate meaningful changes promptly; meaningful ordinary progress
updates already satisfy the cadence without a redundant report. Allow no more
than five minutes of silence during supervision, respecting stricter host timing
with concise updates. Overviews keep active, waiting, returned, and pending-evaluation
work visible with current evidence and next proof while supervision continues.
Stored status does not prove execution. Follow the installed DIRECTION contract's full cadence
and exit rules.

## Update on an explicit request

```text
Update the Director Pattern in this project from https://director.metal-sole.com
```

This public address is the guide's front door; GitHub remains the update source.
Resolve published GitHub main to one exact reviewed SHA and use that revision's
[UPDATES protocol](https://github.com/bladnman/director_pattern/blob/main/pattern/engine/references/UPDATES.md),
even if installed guidance requires an audit on every upgrade or has no protocol.
Read installed guidance for local adaptations; preserve project-owned rules and
host restrictions, resolving conflicts with the accountable owner. The current
INSTALL guide routes existing installations to updates, not through first setup.
While the project is active, only its checked Director initiates a metadata check
at most once per rolling 24 hours. Failed attempts also consume the window; workers
and inactive projects do not start checks. Default to this simple message:
**A new Director Pattern is available. Say “update director pattern” to install it.**
Say **“always update director pattern”** to record project-scoped automatic updates;
notify/off preferences remain durable. Automatic mode follows the same safe update
protocol and stops at unresolved conflicts or migration boundaries. No checking
model, scheduler, or new software is installed.

Back up files to be changed and verify their bytes. Compare installed baseline,
local current files, and incoming revision, including prior upstream and persistent
adaptations. Preserve project state, role index and definitions, enduring
capability/authority policy, and identity roster. Preserve old environment mappings
as history/evidence outside startup; do not promote observations into future rules.
Retained host adapters remain conditional and require current capability checks.
Select checks from the upstream delta and local drift:
routine prose changes need focused file/link and preservation checks; helper-only
changes need compatibility and relevant disposable fixtures. Reuse still-applicable
evidence for unchanged startup. Full startup audits apply to structural startup,
role-routing, or inherited-instruction changes, or detected defects requiring them;
fresh host trials cover only affected behaviors. Missing baselines require safe
reconstruction/review, not automatic startup trials. Carry forward unrelated prior
verification gaps honestly. Newly required blocked checks leave the affected update
incomplete, and partial adoption retains the old accepted revision.

Verify before recording the new revision and report scope, checks, reused evidence,
and limits compactly. An already-current result does not accept unreviewed local
drift. Do not migrate trackers, switch modes, or replace project identity as a side
effect. Preserve the canonical-index pointer and project-owned definitions.
Reviewed reversible adoption may replace a predecessor's startup role default
while keeping its authorized tracker workflow and records; data migration remains
a separate decision. Leave one active startup default.

The public contracts and package control when this summary differs from them.
