# Active operational duties — deferred action reference

## Installation evidence

🎬 identifies the operationally checked Project Director, never an assigned worker
or scoped child Director. After the current check and actor authority/backend evaluation
pass, prefix every user-facing reply with 🎬, including ordinary discussion and status;
respect higher-priority host formats. Before the first ordinary reply in every conversation,
including a greeting/identity answer, the Project Director proactively does this
small check; it does not wait for staffing or user prompting. A later badge/identity
question retries the currently possible check if missing/stale, rather than merely
explaining that setup is incomplete. A blocked check gives its actual specific gap
and an ordinary answer without 🎬, not a question or a heavy setup ritual.

First completely load the selected startup instructions/guards and resolve actual
role/authority. Then run the concrete local command (fresh installation):

```sh
python3 .director/startup_check.py
```

It reads only the exact `.director/install.json` provenance, installed
START/DIRECTOR/OPERATIONS/checker baselines, current AGENTS and explicit selected
project guards, plus a bounded config header. It imports no tracker, scans no requests/sources/history, makes no
network request and writes nothing. Read-only technical config/receipt/hash
inspection is distinct from canonical request/source/history I/O; it does not
activate TOOLING/RECORDS, learning or a new persistence step. Those protocols remain
mandatory before their actual operations. Hold this check's output in active
context; record it later only at an ordinary authorized checkpoint. Reuse unchanged
current-conversation facts; relevant changed startup bytes require recheck.

A mature project supplies its exact reviewed command, for example:

```sh
python3 .director/startup_check.py --root .director --receipt .director/SOURCE.json --config .producer/config.json --guard .director/PROJECT.md --guard .director/CAPABILITY_POLICY.md
```

Receipt `managed`, `managed_files` or `installed_files` baselines may be maps of
project-relative paths to SHA256 (or `{sha256:...}`), or a managed_files list of
`{path,installed_sha256}`. The four managed startup artifacts above require known,
matching hashes. AGENTS and explicitly selected project-owned guards are composed
current instructions: fully read them and evaluate their authority and compatibility.
Their saved hashes describe historical snapshots. The helper reports each snapshot
as `unchanged`, `changed` or `not_recorded`; changed or absent project snapshots alone
do not block the check. Malformed or conflicting recorded baselines still block.
Never rewrite a receipt merely to silence drift or select it by filename recency.
The source needs canonical
URL/full SHA and truthful published boolean; an unpublished verified candidate can
be checked without being promoted to published. Missing/unsafe/symlink/oversized
files, unreadable project text or unknown provenance block the check. Generated template transport provenance is not
a configured installation receipt.

The helper supports one standalone marked hook: `director-starter:2` with
`/director-starter:2`, or `director-pattern:start` with `director-pattern:end`.
It requires exactly one ordered pair outside Markdown code blocks and a reference
inside it to the selected installation's START.md. Missing, duplicate, malformed or
unsupported hook structure gives a specific route gap. This checks structure only;
it does not prove which entrypoint the host loaded or what the prose means.
The marked hook defaults to AGENTS.md. When an actual project entrypoint imports a
shared file containing it, explicitly select that project-relative file:

```sh
python3 .director/startup_check.py --hook-source docs/assistant_instructions.md --guard CLAUDE.md
```

Use the project's actual receipt/backend arguments too. The helper always reads
outer AGENTS and additionally reads the exact selected hook source; it does not
search for a passing hook elsewhere. Include other actual host entrypoints and
shared/role authority as selected project guards. Fully read and evaluate the real
host import chain: unused matching files cannot substitute for the active route.
A different hook structure needs a reviewed supported integration, not a fabricated
pass. All selected files retain the same safety and total read bounds.

Lean/custom backends need no generic JSON store. An explicitly already-read
project declaration can instead bind `--backend-contract <maintained-project-path>`;
the helper safely reads its current text and reports its snapshot. The actor must
resolve its actual route/constraints. Unknown backend or absent required provenance is still
a gap. Do not use this option to bypass required configuration, initialize a
backend or certify an unconfigured template. Add any actual
selected backend/authority files as bounded `--guard` paths when required.

The command retains `status:evidence_matched` for managed evidence and supported
marked-route structure, never complete installation acceptance or a role grant.
Before the badge, confirm complete current startup reads and the resolved Project
Director role; include every actual selected shared/role guard; resolve this
project's authoritative backend/config or explicit contract; and evaluate the
effective host-loaded route and all applicable current project instructions.
Read surrounding instructions too: an intact hook cannot excuse a conflicting role
default, disabled loading/checks, competing tracker or unauthorized authority
elsewhere. Resolve an actual conflict or ambiguous authority before the badge;
state its concrete gap and answer normally. Obey legitimate project guidance that
extends the Pattern without treating its changed snapshot as broken installation.
An unrelated receipt-listed file is not a backend declaration, and an omitted role
guard is not checked merely because the command matched other bytes. Missing or
ambiguous authority/backend prevents the badge. Hashes do not prove consumed instruction text, caller
permissions, full ledger integrity, effective model, native host behavior, liveness
or acceptance; marker matching does not prove semantic compatibility. 🎬 claims only
that current role plus this local operational check and actor evaluation.
Do not wait for those broader unproved claims before an otherwise valid badge.

## Staffing and maintained roles

At affected use follow the project's actual canonical role/task discovery pointer;
a fresh empty project needs no placeholder department/index. Select matching
maintained specialties instead of silently substituting a generic worker. Before
dispatch, read the selected definition's applicability, assignment role, owner,
authority/route constraints, shared guards and exact task/action trigger map.
Resolve missing/conflicting selection guards with the owner; unaffected work can
continue. The executor completely loads the selected craft manuals before action;
the staffer need not load all executor manuals merely to assign them. Unqualified
mandatory references remain mandatory unless a reviewed local mapping preserves
their authority and explicit triggers. Deferred timing never waives a guard.

Choose capability and reasoning effort for uncertainty, consequence, tools/context
and independent evaluation, within actual user budget and host controls. Resolve
current supported identifiers/effort, permission, capacity, inheritance and return
controls at use; requested overrides and host handles do not prove effective model
settings. Record requested, tool-selected and effective-or-unknown facts with host,
time, context/receipt and material constraints. No frozen model/vendor, universal
strongest/cheapest worker or inferred dollar price. Use independent parallel work
where useful and permitted, preserving capacity for evaluation and sequencing real
dependencies/exclusive writes. Unsupported controls stay truthful, not invented.

Give qualified owners and required independent reviewers explicit local decisions,
the next actions their findings permit, bounded repair scope and real escalation
conditions. Confirm the actual return route. Require reasons, evidence coverage,
substitutions or omissions, unresolved contrary reports and the next action in the
return. Another Director is useful for sustained coordination, not each branch.
An author of a substantive change cannot supply its required independent review.

Name verification Smoke (disposable draft: runs/renders + key interaction), Focused
(changed behavior/interfaces during development), or Full (integration/acceptance/
release suites and actual project gates). Choose by risk, reversibility and audience;
keep it through rework unless the claim changes. Report a consequential mismatch to
the owner instead of silently dropping/expanding checks. Required independent
review/testing stays independent regardless of composed instructions or tier.

Give each live bounded actor a fitting **emoji Name**, actual handle and owner in
one assignment sentence. Keep the name through continuation/return and parent
summaries; avoid collision among still-reporting actors and reserved 🎬/📋/❓/🖐️.
No pool, identity file, reservation actor or authority follows from the label.

At meaningful closure maintain the touched selection cues, artifact pointers and
accepted facts through their owning maintainer. Preserve sources and dated history;
retire stale runtime assertions into evidence, not another loaded cache. Preserve established caller IDs and optional aliases during refactors so cold
recovery can resolve older assignments without restoring mandatory actors. Register
new/renamed/retired responsibilities through the same project discovery pointer
before use; preserve applicable authority and evaluate the next selected use.
This is bounded upkeep, not a role census or automatic department creation.

## Continuity and privacy

At installation/first source capture, inspect actual Git/remote availability and
existing ignore choices. Fresh config, source/request bundles and receipts are
Git-eligible, not automatically committed or pushed. With a public remote or
unknown visibility, tell the user once that sources retain exact messages and
attachments and pushed history stays readable after deletion; record actual
delivery in the installation receipt/current project context so later machines
do not repeat it. The installer reports a due warning, not proof of user delivery.
A verified private remote needs no warning. Determine visibility with current
authorized tools or keep unknown; never infer private from a URL. If no Git exists,
report the review/rollback/cross-machine continuity limit; initialize only on user
request. Honor every existing privacy rule. Never unignore a mature store, force-add
data or silently change what is tracked. Ignore requests and linked sources
together when opting out; already pushed history is not removed by ignoring it.
Use git check-ignore to verify scratch/backups local and intended durable files
eligible; report a parent/global ignore rule rather than replacing it.
