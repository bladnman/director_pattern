# 🎬 and the check: meaning, failures and changes

For the Project Director only. Workers and scoped child Directors run no check, perform no root first-use setup and never show or inherit 🎬. Paths are in `.director/`.

## What 🎬 claims

🎬 claims three things and nothing more: you resolved your role as Project Director; your own run of the project section's check command, after the latest compaction or resume, reported `status: evidence_matched`; and you confirmed its `actor_must_confirm` items. Then prefix every user-facing reply with 🎬, including discussion, progress and status, until the next break; respect higher-priority host formats.

`evidence_matched` covers managed file hashes and the marked block's structure only. It is never installation acceptance or a role grant. Hashes do not prove consumed instruction text, caller permissions, full ledger integrity, effective settings, native host behavior, liveness or acceptance; marker matching does not prove semantic compatibility. Do not wait for those broader unproved claims before an otherwise valid badge.

## Confirm before the badge

- **Guards.** The project section has two lists. Read every "before your first reply" file completely before the check and the badge; those are the instructions you confirm as complete and free of conflict. Read each "before named work" file completely before that work. The check command names every listed guard; an omitted guard is not checked merely because the command matched other bytes.
- **Backend.** Resolve this project's authoritative request store: its config, or the explicit contract the project section names. An unrelated receipt-listed file is not a backend declaration. Missing or ambiguous authority or backend prevents the badge.
- **Loaded route and conflicts.** Evaluate the instructions the host actually loaded, including text outside the block. An intact block cannot excuse a conflicting role default, disabled loading or checks, a competing tracker or unauthorized authority elsewhere. Resolve an actual conflict or ambiguous authority before the badge. Obey legitimate project guidance that extends the Pattern; a `changed` snapshot of AGENTS.md or a guard is local composition, not a broken installation.

## When the check fails or cannot run

Give the check's actual `gap` and an ordinary answer in the same turn, without 🎬. It is not a question to the user or a heavy setup ritual, and it does not wait for staffing or a task. Then:

- The command was refused or could not run (permission, missing runtime): say exactly that, give the user the 🖐️ action that would allow it, and rerun when possible.
- `project section missing`, or the block routes to a redirect stub: this project's update is unfinished; follow [UPDATES.md](../UPDATES.md), "Move to the AGENTS.md block".
- `Director block differs from its recorded baseline`: the managed block was edited. Restore it from the installed revision; project wording belongs in the project section. Only a reviewed update records a new block. `Director block has no recorded baseline`: the receipt lacks `director_block_sha256`; a reviewed update records it after comparing the block with the installed revision.
- The project section has no check command or is over 3,000 bytes: restore its `Check command` line, or move the roster to `.director/ROSTER.md` and name it there.
- The receipt is absent in a generated project that still awaits setup: that is first use, not a broken install; read [FIRST_USE.md](../FIRST_USE.md) and follow it before the check.
- `startup baseline mismatch`: a managed file changed. Restore it or run a reviewed update. Never rewrite a receipt to silence drift, and never pick a receipt by recency.
- Hook, receipt, source or backend gaps: read [OPERATIONS.md](../OPERATIONS.md) for the supported structures and the exact command options.

A later badge or identity question reruns the currently possible check; do not merely explain that setup is incomplete.

## When to run it again

After every compaction or session resume; when an opt-out ends; and when startup bytes change: AGENTS.md, the block or project section, a guard, a managed file, the receipt or the config. Reuse an unchanged result within one uninterrupted conversation.

## What the check does

It reads only the selected receipt, the installed baselines of WORKER.md, OPERATIONS.md, the cards, the two redirect stubs and the checker, current AGENTS.md, the selected guards, a bounded config header and the local update-check cache. It imports no tracker, scans no requests, sources or history, makes no network request and writes nothing, so it needs no store manuals and no checkpoint write. Hold its output in context; record it later only at an ordinary authorized checkpoint. No checker actor is needed.

If a higher-priority host requires startup progress, give only an honest unbadged checking note first. It gives no greeting or identity answer and no setup or completion claim. Do not promise silent startup across hosts.

In a generated project whose setup receipt is absent, the project section lists first use before the check: read [FIRST_USE.md](../FIRST_USE.md) and its required reads completely, run its guarded `ensure`, then run the check. Successful setup earns no badge by itself.

Before changing the check command, the hook source or how instructions load, read all of OPERATIONS.md; afterwards rerun the check.
