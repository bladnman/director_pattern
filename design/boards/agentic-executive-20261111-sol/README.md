## Present

- **→ / Next** moves one cue forward, including into the next topic.
- **← / Previous** moves backward, including into the previous topic.
- **R / Replay** restarts the current cue. **Home** opens the topic's first cue.
- **Space / Pause / Resume** freezes or resumes an active cue. A settled cue is
  already held; Replay starts it again. Space retains normal button behaviour
  when a button has focus.
- The topic selector opens a topic. The short bars jump to its cues.
- A link such as `presenter.html#learning~5` opens a cue; numbering starts at one.
- With reduced motion enabled, each cue immediately displays its settled state.

## A briefing in under ten minutes

Allow about 1:20 for each topic and a minute for the opening and close. Most cues
need one or two spoken sentences; the six learning cues divide the same allotted
time into shorter visual beats.

1. **A domain system — 1:20.** Begin with the problem the organisation wants to
   handle repeatedly. The boundary follows that problem, rather than copying a
   human reporting structure. Agents coordinate around retained context; people
   no longer have to reconstruct every handoff across isolated assistant sessions.
   Show request in, parallel work with uneven return times, and one response out.
2. **The Director Pattern — 1:20.** One coordinator retains the request and its
   conditions, assigns bounded work and evaluates the combined result. Traceable
   work and shared domain history, guidance, guardrails and tools make it possible
   to diagnose and improve the system. A local role can apply centrally maintained
   design guidance; every domain need not recreate its own standards.
3. **Learning and adaptation — 1:20.** A correction is evidence. After review, a
   useful domain lesson becomes maintained guidance. The next matching task uses
   that lesson and passes its check. Then distinguish changing the instructions
   from changing the structure: an Architect inspects recurring demand and rework,
   adds a useful responsibility, and retires an underused one.
4. **Across systems — 1:20.** Start with an empty pending collection. A write creates
   rows; there are no reserved recipient boxes. When a recipient is ready, it asks
   for its items. Matching rows leave the pending collection. A reply uses the same
   route. Each domain keeps ownership of its work and evaluates what it receives.
5. **People — 1:20.** People provide input, collect questions and return decisions
   through the same exchange. Work needing a decision waits; other work may
   continue. A reply unlocks the relevant work when the Director collects it. A
   domain can start usefully while another department still works through people;
   it does not need every department to build a system first. Human-created design
   material can arrive here and be checked by a local design responsibility.

6. **Across the organisation — 1:20.** Keep the familiar domain as the anchor and
   pull back to reveal neighboring systems, then many differently shaped and sized
   domains. Each retains its own context. A few Directors coordinate through the
   shared exchange; the organisation does not become one giant team. Start where a
   domain is useful, then connect other domains as the work earns it.

Close with the practical proposal: build teams that create and maintain systems
around valuable domains, with explicit human authority and evidence of improvement.

## What this demonstrates

The diagrams simulate work, messages, retained guidance and structural changes.
No agent execution, transport, scheduler, file-writing service or organisation is
created by the presenter. File glyphs mean durable records, without prescribing
their format. Branches can be agents, teams or maintained responsibilities.

Learning is shown as evidence, review, maintained guidance and later use. The
Architect and dynamically shared message exchange are proposed operating concepts;
they are not claims that an automatic Architect or transport is installed in the
current method. Growth and retirement remain subject to the domain's authority
and review. This visual exploration changes no runtime instructions.

Native interaction checks and independent review support the reviewable prototype.
Owner creative acceptance and effectiveness with a real executive audience remain
open. No site publication, release or installation is performed.
